# ActionLens Vision 1.0

## 1. 文档目标

本文档定义 ActionLens 在第一阶段采用的技术路线与 AI 输出目标，服务于以下方案：

`系统截图 + OCR + 云端 LLM + EventKit`

本版明确三件事：

- Vision 1.0 要做成什么
- DeepSeek V4Flash 在后端承担什么角色
- 如何通过解释层、校验层和重置机制保证输出稳定可用

## 2. Vision 1.0 目标

### 2.1 产品目标

在 macOS 上，用户按下快捷键截图后，系统能够：

1. 读取截图中的主要文本
2. 判断截图属于哪一类内容
3. 生成结构化、可编辑、可写入提醒事项的结果
4. 在失败时自动修复或重试
5. 在无法可靠生成时明确降级，而不是胡乱输出

### 2.2 Vision 1.0 成功标准

Vision 1.0 不是“让模型看图自由发挥”，而是要求：

- 输出格式固定
- 输出字段可解析
- 输出内容可解释
- 输出失败可重试
- 输出偏移可被拦截

## 3. 第一阶段范围

### 3.1 输入

- 用户截图图片
- Vision OCR 提取出的文本
- 基础上下文信息：
  - 时间戳
  - 语言猜测
  - 文件来源

### 3.2 输出

系统输出一个结构化结果对象，用于前端展示和 Reminders 写入。

### 3.3 首批支持场景

Vision 1.0 首先聚焦以下三类高确定性场景：

- `meeting_notes`
- `course_notice`
- `job_description`

以下两类保留支持，但默认标记为“生成型场景”，需要更强解释与确认：

- `event_poster`
- `travel_guide`

## 4. 后端模型策略

## 4.1 模型选型

Vision 1.0 后端默认模型：

- `DeepSeek V4Flash`

### 选型理由

- 响应速度优先，适合截图后即时返回
- 适合结构化抽取与分类任务
- 成本更适合高频截图场景

## 4.2 模型职责

DeepSeek V4Flash 不直接负责“替系统做一切”，而是只负责以下任务：

1. 基于 OCR 文本和少量截图上下文进行内容分类
2. 从内容中抽取行动项
3. 生成固定 JSON
4. 给出必要的解释字段和置信度信号

不让模型直接做的事：

- 不直接写入 Apple Reminders
- 不直接决定最终保存结果
- 不直接绕过 schema 校验
- 不直接向用户展示未经校验的原始输出

## 5. 核心架构

Vision 1.0 推荐采用以下链路：

`截图 -> OCR -> 解释层 -> LLM -> 结果校验 -> 修复/重置 -> 前端确认 -> EventKit`

### 5.1 分层说明

#### A. OCR 层

职责：

- 从截图中提取尽可能完整的原文
- 提供多行文本与基础置信度

#### B. 解释层

职责：

- 把 OCR 原文整理成模型更容易理解的输入
- 识别文本结构，如标题、时间、条目、链接、要求项
- 限制模型任务范围
- 生成稳定 prompt 和输出契约

#### C. LLM 结构化层

职责：

- 基于解释层输入产出固定 JSON

#### D. 校验层

职责：

- 校验字段是否齐全
- 校验 JSON 是否合法
- 校验内容类型与结果是否匹配
- 校验是否存在明显偏移

#### E. 修复与重置层

职责：

- 当返回格式错误时修复
- 当语义偏移时重做
- 最大重置 5 次

## 6. 解释层设计

这是 Vision 1.0 的关键层。

## 6.1 为什么必须有解释层

如果直接把 OCR 文本扔给模型，常见问题包括：

- 把说明文字误识别成任务
- 把噪音文本当主内容
- 输出字段漂移
- 在“海报/攻略”这类场景里过度脑补

解释层的目标不是替代模型，而是**收窄模型的发挥空间**。

## 6.2 解释层输入

解释层接收：

- 原始 OCR 文本
- 截图基础元信息
- 用户语言偏好
- 规则模板

## 6.3 解释层输出

解释层向模型输出一个标准输入包：

```json
{
  "raw_text": "...",
  "normalized_text": "...",
  "suspected_type_candidates": ["meeting_notes", "course_notice"],
  "extracted_signals": {
    "has_deadline": true,
    "has_bullets": true,
    "has_company_name": false,
    "has_salary_info": false
  },
  "instruction_profile": "task_extraction_strict"
}
```

## 6.4 解释层必须做的事

- 文本清洗：去掉明显噪音、重复空行、乱码片段
- 结构归一：把列表、编号、标题、时间字段提出来
- 场景预判：先给出 1 到 3 个候选类型
- 任务边界约束：告诉模型“只提取能转成提醒事项的项”
- 生成型场景降级：对海报、攻略这类内容提示模型“只生成保守计划，不要过度发挥”

## 7. 标准输出契约

Vision 1.0 统一要求模型输出以下 JSON：

```json
{
  "content_type": "meeting_notes",
  "title": "项目例会纪要",
  "summary": "本次会议涉及登录页修复和发布时间调整",
  "confidence": 0.86,
  "explanation": {
    "reasoning_summary": "截图包含会议式条目和待办描述，因此归类为 meeting_notes。",
    "key_signals": [
      "出现了多条行动项",
      "存在时间节点",
      "语气为内部跟进而非宣传"
    ]
  },
  "items": [
    {
      "title": "修复登录页按钮样式",
      "kind": "todo",
      "due_date": null,
      "priority": "medium",
      "notes": "负责人未明确",
      "source_span": "第 2 条：修复登录页按钮样式"
    }
  ],
  "needs_review": false
}
```

## 7.1 字段约束

- `content_type`：必须属于白名单枚举
- `title`：不能为空，长度限制 80 字内
- `summary`：简短摘要，长度限制 200 字内
- `confidence`：0 到 1
- `explanation.reasoning_summary`：必须给出一句可读解释
- `items`：数组，可为空，但必须存在
- `needs_review`：布尔值

## 7.2 content_type 白名单

- `meeting_notes`
- `course_notice`
- `job_description`
- `event_poster`
- `travel_guide`
- `generic`

## 8. 鲁棒性策略

## 8.1 三层防线

### 第一层：Prompt 约束

- 只允许输出 JSON
- 明确字段和枚举
- 明确禁止额外解释性废话
- 对生成型场景要求保守输出

### 第二层：程序校验

- JSON 语法校验
- schema 校验
- 枚举合法性校验
- 字段长度校验
- 空值与类型校验

### 第三层：语义校验

程序做二次判断：

- `meeting_notes` 是否真的包含动作型条目
- `job_description` 是否真的包含岗位、职责、要求信号
- `course_notice` 是否真的包含课程、作业、考试或截止信息

如果分类和文本信号严重不匹配，视为偏移。

## 8.2 常见偏移类型

- 类型偏移：会议截图被识别成活动海报
- 任务偏移：模型凭空生成截图中不存在的任务
- 结构偏移：字段缺失或命名错乱
- 强行总结：明明没有任务，却硬凑出待办

## 8.3 偏移拦截原则

一旦命中以下任一情况，结果不得直接进入前端主展示：

- JSON 不合法
- schema 不合法
- `content_type` 不在白名单
- 任务条目明显来自幻觉
- explanation 缺失
- confidence 低于阈值且场景属于生成型内容

## 9. 重置机制

## 9.1 定义

这里的“重置”不是简单重复请求，而是对模型调用上下文进行重新构建后再次生成结果。

每次重置都要带着失败原因进入下一轮，而不是原样重试。

## 9.2 最大次数

- 最大重置次数：`5`

超过 5 次后，系统进入失败降级模式。

## 9.3 重置触发条件

以下情况触发重置：

1. 返回内容不是合法 JSON
2. 缺少关键字段
3. 枚举值非法
4. 语义校验失败
5. 幻觉任务比例过高
6. 解释字段缺失

## 9.4 重置策略分级

### 第 1 次重置：格式修复

- 明确提示“上次输出不是合法 JSON”
- 要求只返回契约字段

### 第 2 次重置：结构修复

- 指出缺失字段或非法枚举
- 回传 schema 错误信息

### 第 3 次重置：类型修复

- 指出 `content_type` 判断不可信
- 提供解释层候选类型重新约束

### 第 4 次重置：任务收缩

- 明确要求只保留截图中证据最充分的任务
- 删除脑补项

### 第 5 次重置：保守降级

- 如果仍不稳定，只要求输出：
  - `content_type`
  - `title`
  - `summary`
  - `items: []`
  - `needs_review: true`

## 9.5 五次失败后的最终降级

如果 5 次重置后仍失败：

- 不再继续调用模型
- 前端展示 OCR 原文
- 标记为“AI 解析失败，请手动整理”
- 允许用户手动创建提醒事项

这样可以保证系统不会陷入无限重试，也不会把错误结果写进 Reminders。

## 10. 提示词策略

## 10.1 系统提示词原则

- 角色固定：截图结构化助手
- 输出固定：只输出 JSON
- 分类固定：仅允许白名单类型
- 生成边界固定：只输出可被 Reminders 使用的信息

## 10.2 业务提示词原则

每类场景使用不同模板：

- `meeting_notes`：偏任务抽取
- `course_notice`：偏学习安排
- `job_description`：偏申请步骤
- `event_poster`：偏参加准备
- `travel_guide`：偏保守 itinerary

## 10.3 解释字段要求

模型必须回答两个解释问题：

1. 为什么判断成这个类型
2. 每个任务依据来自哪里

这能帮助我们：

- 给用户更强的信任感
- 排查模型为什么偏移
- 做后续评估与 prompt 调优

## 11. Reminders 映射原则

只有通过校验层的 `items` 才允许进入 EventKit。

映射规则：

- `item.title` -> reminder title
- `item.notes` + `source_span` -> reminder notes
- `item.due_date` -> due date
- `item.priority` -> priority

以下情况默认不自动写入：

- `needs_review = true`
- `confidence` 低于阈值
- `items` 为空

## 12. Vision 1.0 的工程目标

第一阶段要先实现以下工程能力：

- 固定 JSON schema
- 解释层输入构建器
- DeepSeek V4Flash 调用封装
- 响应校验器
- 5 次重置机制
- 失败降级展示

## 13. 明确不做的事

Vision 1.0 暂不追求：

- 通吃所有截图类型
- 完全自动无确认写入提醒事项
- 靠单次模型调用解决全部问题
- 用长链推理替代程序约束
