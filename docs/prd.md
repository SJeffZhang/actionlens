# ActionLens PRD v1

## 1. 文档目的

本文档定义 `ActionLens` 第一阶段产品方向。  
产品目标是做成一个 **macOS 截图工具 App** ：用户通过快捷键唤起截图，系统理解截图内容，自动生成任务或计划，并最终写入苹果提醒事项。

## 2. 产品定义

### 2.1 产品一句话

ActionLens 是一个把截图内容自动转成提醒事项的 macOS AI 助手。

### 2.2 核心价值

用户在屏幕上看到重要信息时，不需要再经历：

- 截图
- 手动打开备忘录或提醒事项
- 再手动整理任务

而是变成：

`快捷键截图 -> 自动理解 -> 一键生成提醒事项`

## 3. 背景与机会

用户日常会截图保存很多信息，但大多数截图都停留在“存档”，没有进入后续行动流。

典型例子：

- 课程通知 -> 需要安排学习
- 会议截图 -> 需要整理 TODO
- 活动海报 -> 需要决定是否参加并做准备
- 招聘 JD -> 需要拆成申请任务
- 旅行攻略 -> 需要整理 itinerary

现有系统截图工具解决了“截下来”，但没有解决“接下来做什么”。

ActionLens 的机会点，就是把截图从“静态图片”变成“行动入口”。

## 4. 目标用户

### 4.1 核心用户

- 学生：从课程通知、作业说明中生成学习任务
- 职场用户：从会议截图、聊天截图中生成 TODO
- 求职者：从招聘 JD 中生成申请流程任务
- 旅行用户：从攻略截图中生成行程计划

### 4.2 用户痛点

- 截图很多，但很少被真正处理
- 手动整理任务成本高
- 信息散落在聊天、网页、海报、文档里
- 想用系统提醒事项，但录入步骤太多

## 5. 产品目标

### 5.1 第一阶段目标

- 支持快捷键唤起截图
- 截图后自动识别主要内容
- 自动生成结构化任务或计划
- 允许用户确认、编辑
- 一键写入 Apple Reminders
- 建立稳定的解释层与输出校验机制
- 在 AI 输出失败时支持自动重置，最大重置次数为 5 次

### 5.2 非目标

第一阶段暂不做：

- 团队协作
- 云同步
- 多人共享任务
- iPhone / iPad 客户端
- 与 Notion、Linear、Jira 的集成
- 完整截图编辑器

## 6. 核心使用场景

### 场景 1：课程通知

输入：课程群公告、作业通知、考试安排截图  
输出：学习计划、复习提醒、截止时间任务

### 场景 2：会议截图

输入：会议纪要截图、聊天记录截图、白板截图  
输出：TODO 列表、待确认事项、跟进提醒

### 场景 3：活动海报

输入：讲座、展览、线下活动海报  
输出：是否参加提醒、报名任务、出发准备事项

### 场景 4：招聘 JD

输入：招聘信息截图、岗位 JD 截图  
输出：投递任务、简历修改任务、准备作品集任务

### 场景 5：旅行攻略

输入：小红书/网页攻略截图、路线图截图  
输出：行程安排、预订提醒、打包清单

## 7. 用户流程

### 7.1 主流程

1. 用户按下全局快捷键
2. 系统进入截图状态
3. 用户选择区域或窗口
4. App 获取截图
5. AI 识别截图内容
6. App 输出“内容类型 + 结构化任务/计划”
7. 用户确认或编辑
8. 用户点击“添加到提醒事项”
9. App 将内容写入 Apple Reminders

### 7.2 失败兜底流程

1. AI 无法准确识别
2. App 仍展示 OCR 原文与低置信度结果
3. 用户可手动编辑后保存到提醒事项

## 9. 核心功能需求

### 9.1 菜单栏与快捷键

需求：

- App 以 macOS 菜单栏工具运行
- 支持设置一个全局快捷键
- 按下快捷键后立即进入截图模式
- 首次启动时提供权限引导

验收标准：

- App 不需要每次手动打开主窗口
- 快捷键在 App 非前台时也能触发

### 9.2 截图能力

需求：

- 支持区域截图
- 支持窗口截图
- 截图完成后自动进入识别流程

第一阶段实现建议：

- 优先复用系统截图能力
- 后续再升级为自定义截图体验

### 9.3 OCR 与内容理解

需求：

- 从截图中提取主要文字
- 自动识别截图类型
- 基于类型输出对应结构
- 使用解释层收窄模型输出空间
- 使用 DeepSeek V4Flash 作为 Vision 1.0 默认后端模型

支持的类型：

- `course_notice`
- `meeting_notes`
- `event_poster`
- `job_description`
- `travel_guide`
- `generic`

### 9.4 结构化输出

建议输出模型：

```json
{
  "content_type": "meeting_notes",
  "title": "项目例会",
  "summary": "会议围绕发布时间和登录页问题展开",
  "items": [
    {
      "title": "修复登录页按钮样式",
      "kind": "todo",
      "due_date": null,
      "priority": "medium",
      "notes": "负责人未明确"
    }
  ]
}
```

字段说明：

- `content_type`：内容类型
- `title`：截图主题
- `summary`：截图摘要
- `items`：要生成到提醒事项中的行动项

Vision 1.0 额外要求：

- 模型必须输出固定 JSON
- 模型必须输出解释字段，说明类型判断依据
- 每个任务应尽可能保留来源片段
- 输出在进入前端前必须经过程序校验

### 9.5 结果确认与编辑

需求：

- 用户可编辑标题
- 用户可编辑每条任务
- 用户可删除模型误判内容
- 用户可手动新增任务
- 用户可选择写入哪个提醒事项列表

这是第一阶段必须保留的步骤。  
原因是 AI 的任务生成存在主观性，不能默认直接写入提醒事项。

当系统命中以下条件时，结果必须强制进入人工确认：

- `needs_review = true`
- 模型重置后仍未稳定
- 置信度过低
- 属于生成型场景，如 `event_poster` 或 `travel_guide`

### 9.6 Apple Reminders 集成

需求：

- 请求提醒事项访问权限
- 读取用户已有 reminder lists
- 选择目标 list
- 写入一个或多个 reminder

可映射字段：

- 标题 -> reminder title
- 备注 -> reminder notes
- 截止时间 -> due date
- 优先级 -> reminder priority

只有通过解释层和校验层的结果才允许写入提醒事项。

## 10. 产品策略

## 10.1 第一阶段先做“任务导向”最强的场景

建议优先把以下三类做扎实：

- 会议截图
- 招聘 JD
- 课程通知

原因：

- 结构更清楚
- 输出更容易验证
- 更适合直接映射到提醒事项

### 10.2 活动海报和旅行攻略作为“计划生成型”场景

这两类可以支持，但在产品表达上要说明：

- 不只是提取已有任务
- 还会根据内容自动生成建议计划

## 11. 交互要求

### 11.1 首次使用

- 展示欢迎页
- 引导用户授权截图权限
- 引导用户授权提醒事项权限
- 引导设置快捷键

### 11.2 截图后结果面板

建议包含：

- 缩略图预览
- 内容类型标签
- 标题
- 摘要
- 可编辑任务列表
- 目标提醒事项列表选择器
- “添加到提醒事项”按钮

### 11.3 成功反馈

写入成功后应显示：

- 已写入多少条提醒事项
- 写入到了哪个 list
- 可一键在 Reminders 中打开查看

## 12. 技术建议

### 12.1 技术栈

- 平台：macOS
- 语言：Swift
- UI：SwiftUI
- OCR：Vision
- AI：云端 LLM，Vision 1.0 默认使用 `DeepSeek V4Flash`
- Reminders：EventKit

### 12.2 Vision 1.0 稳定性要求

- 必须存在解释层，不能直接把 OCR 原文裸传给模型
- 必须存在 schema 校验层
- 必须存在语义偏移拦截
- 必须存在自动重置机制
- 单次解析最大重置次数为 `5`
- 超过 5 次后必须降级为“展示 OCR 原文 + 手动整理”

### 12.3 建议的版本基线

建议 v1 目标系统为：

- `macOS 14+`

理由：

- EventKit 提醒事项权限模型更清晰
- 能兼顾较新的系统能力与实际覆盖面

## 13. 成功指标

### 13.1 产品指标

- 从快捷键触发到结果展示 <= 6 秒
- 用户确认后写入提醒事项成功率 >= 95%
- AI 首次输出可直接编辑使用率 >= 70%

### 13.2 体验指标

- 首次授权流程用户可在 2 分钟内完成
- 常见场景下生成结果不超过 1 次手动大改

## 14. 风险与挑战

- 屏幕捕获权限会影响首启转化
- OCR 对模糊图、手写图效果有限
- AI 可能误把说明性文字当成任务
- “活动海报 / 旅行攻略”场景更偏建议生成，稳定性比会议类场景低
- 模型输出可能出现格式漂移、字段缺失或语义偏移

对应策略：

- 用解释层限制模型自由度
- 用固定 schema 拦截结构问题
- 用语义校验拦截内容偏移
- 用最多 5 次重置机制做恢复
- 失败后强制降级，不把异常结果写进 Reminders
